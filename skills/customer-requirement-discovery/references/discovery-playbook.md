# 需求发现方法

## 1. 先建立台账

每次只在内部维护，不直接外发：

| 区域 | 记录内容 |
| --- | --- |
| 已确认事实 | 客户或内部用户明确说过、可追溯的信息 |
| 假设 | 为继续讨论临时采用但尚未确认的判断 |
| 未知项 | 可能改变目标、流程、可行性、范围或验收的信息 |
| 冲突 | 两个陈述不能同时成立，或目标与约束互相抵触 |
| 风险 | 数据、合规、效果、依赖、运营或交付风险 |
| 证据来源 | 客户原话、会议纪要、附件、内部说明或产品文档 |

不得把“行业一般如此”升级为客户事实。推断必须进入假设区。

## 2. 动态扫描维度

以下是扫描维度，不是固定问卷：

| 维度 | 需要知道什么 | 只在何时追问 |
| --- | --- | --- |
| 目标与决策 | 谁要做出什么更好的决策，当前损失是什么 | 目标只是“做 AI/Agent/平台”时 |
| 用户与场景 | 谁在什么时点使用，前后动作是什么 | 用户或流程会改变产品形态时 |
| 输入 | 数据、文件、指令、权限和来源 | 输入可得性影响可行性时 |
| 核心处理 | 分类、检索、生成、预测、审批还是执行 | 客户用抽象词掩盖多个能力时 |
| 输出与去向 | 看板、清单、文件、消息、系统动作 | 输出决定 UI、集成或闭环时 |
| 运行机制 | 人触发、定时、事件触发、人工审核 | 自动化程度影响风险与工作量时 |
| 约束 | 合规、隐私、版权、预算、部署、语言 | 约束可能否决方案时 |
| 验收 | 谁用什么样本、指标和流程判断有效 | “准确”“智能”“提升效率”未量化时 |
| Demo 目标 | 演示、验证流程、验证模型还是确认界面 | 用户提出 Demo 时 |

平台、数量、频率、时效、准确率、国家地区等只作为条件变量。只有它们会改变数据路径、容量、成本、合规或验收时才问。

## 3. 每轮选题

给每个候选问题做内部排序：

`优先级 = 决策影响 × 当前不确定度 × 内部可回答性`

选择 1-3 个最高项。优先问内部用户最可能知道、且能减少客户问题数量的内容。问题要短，必要时给 2-4 个互斥例子帮助回答，但不要诱导成既定方案。

## 4. 成熟度

| 等级 | 判定 | 下一步 |
| --- | --- | --- |
| M0 线索 | 只有方向或口号 | 继续内部需求发现 |
| M1 场景 | 目标用户与核心任务大致清楚 | 补输入、输出和边界 |
| M2 闭环 | 输入、处理、输出和人工节点清楚 | 生成客户澄清清单 |
| M3 可评估 | 数据、依赖、约束和验收基本清楚 | 做可行性与产品适配 |
| M4 可交接 | 关键未知项已关闭或转为明确验证项 | Demo、报价范围或 PRD |

连续两轮没有新增高影响信息时，不再追加内部轮次，转成最终客户清单。

## 5. 停止条件

满足任一条件即停止内部访谈：

- 已达 M2，剩余信息只能由客户确认；
- 连续两轮没有新增高价值信息；
- 已进行五轮；
- 内部用户明确要求立即生成客户清单。

停止不等于需求已经可报价。要明确当前成熟度和仍需客户回答的关键项。

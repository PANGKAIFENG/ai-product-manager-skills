# 证据化描述契约

## Evidence Ledger

| 等级 | 可用来源 | 写法 |
| --- | --- | --- |
| `已验证` | 日志、代码、接口结果、截图、可重复操作、云效字段、用户明确事实 | 陈述直接观察，不扩展到证据没有证明的原因 |
| `有依据的推断` | 两项以上一致证据，或现象与代码路径共同支持 | 写明推断链和仍缺少的直接验证 |
| `弱推断` | 单一现象、经验类比、不完整截图 | 只能作为排查方向，不能作为根因 |
| `待验证` | 关键事实缺少证据 | 写清最小验证动作和对结论的影响 |

每条证据包含：

```text
[等级][类型] 来源引用
观察：证据中可以直接看到什么
支持：这条证据支持哪个结论
边界：它没有证明什么（仅在容易误读时填写）
```

可用类型：`日志`、`代码`、`接口`、`截图`、`复现`、`文件`、`用户陈述`。

## 缺陷描述模板

```text
【问题现象】
<用户在什么条件下遇到什么异常，以及当前绕路。>

【复现步骤】
1. <步骤>
2. <步骤>
3. <观察结果>

【实际结果】
<当前系统表现。>

【期望结果】
<用户可观察、可验证的正确行为。>

【排查证据】
1. [已验证][日志] <路径:行号、时间或 trace ID>
   观察：<直接观察>
   支持：<支持的结论>
2. [有依据的推断][代码] <文件:行号>
   观察：<直接观察>
   支持：<推断>

【排查结论】
- 已确认：<证据直接支持的结论。>
- 推断：<尚未直接验证的因果判断。>
- 待验证：<会影响方案或验收的最小未知项。>

【影响范围】
<受影响用户、场景、版本；未知时写“尚未确认”，不要估算。>

【验收标准】
1. <Given/When/Then 或明确操作与结果。>
2. <当前会话、数据一致性或失败路径要求。>
3. <不得发生的回归。>
```

至少保留：`问题现象、期望结果、排查证据、排查结论、验收标准`。没有复现步骤或影响数据时保留章节并写明缺失状态。

## 需求描述模板

```text
【需求背景】
<谁在什么流程遇到什么限制；区分已确认事实与假设。>

【目标与价值】
<希望形成的用户结果或业务结果，不写未经验证的收益数字。>

【范围】
- 包含：<本工作项负责的能力边界。>
- 不包含：<明确排除的相邻能力。>

【排查证据】
1. [已验证/有依据的推断/弱推断][来源类型] <引用>
   观察：<直接观察>
   支持：<它为何支持本需求>

【方案约束】
<来自现有架构、权限、兼容性或产品边界的约束；不要把建议方案写成唯一实现。>

【验收标准】
1. <可观察结果。>
2. <异常或失败路径。>
3. <数据、权限或兼容性边界。>

【待确认项】
- <只保留会改变范围、优先级或验收的未知项。>
```

至少保留：`需求背景、目标与价值、范围、排查证据、验收标准`。本轮没有证据时，在证据章节写“本轮未提供可复核证据”，不要虚构引用。

## 敏感信息处理

- 日志只摘录支持判断的最小片段，优先给路径、行号、trace ID 和摘要。
- Token、Cookie、Authorization header、密钥和连接串必须完全移除。
- 用户名、手机号、客户数据、文件内容按最小必要原则脱敏。
- 本地绝对路径可能包含个人用户名；提交前优先改成仓库相对路径或稳定日志标识。
- 截图写入描述时只记录观察结论和可访问附件引用，不嵌入本机临时路径。
- 用户要求上传附件时，描述使用最终上传文件名，例如 `evidence.png`。预览同时展示文件类型和大小，但不展示本机临时路径。
- 上传前人工或视觉检查截图中的账号、客户名称、文件路径、Token、Cookie 和内部 payload；无法判断是否敏感时停止上传并请求用户确认脱敏版本。

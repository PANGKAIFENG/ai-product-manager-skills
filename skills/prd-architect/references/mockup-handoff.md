# Mockup Handoff Reference

按需加载本文件。用于 PRD 涉及既有页面、弹窗、面板、按钮、表单、状态提示、HTML mockup 或截图承接时。

## Boundary

`prd-architect` 负责页面型 PRD 的完整 UI 证据链编排，视觉实现由 `ui-mockup-desktop-workbench` 承接，但不能把它留成用户后续再发起的任务。

- 页面型默认交付：PRD、项目 UI 对齐 HTML/preview、关键状态截图、对应章节内嵌证据。
- 正式 UI mockup：调用 `ui-mockup-desktop-workbench` 完成；默认在独立产物目录使用 `visual-handoff`，不改生产前端。
- 发布版 PRD：截图和状态说明应出现在对应功能模块下；本地 HTML、PNG、Look up 或 mock 链接只作为本地草稿信息，不进入线上正文。

## Existing Project Rule

当需求发生在已有产品页面上，先定位：

1. 真实项目。
2. 真实 app / 路由。
3. 真实组件。
4. 用户触发动作。
5. 当前页面状态。

不要凭空画一个新页面代替真实项目页面。

## UI Source Resolution Gate

把“找到一个看起来像前端的目录”和“确认真实 UI 基线”分开处理：

1. 用户明确给出 repo/app/route 时，验证目标页面和组件确实存在。
2. 未给出路径时，可以发现候选，但只有唯一候选且产品标识、路由或组件证据一致时才直接使用。
3. 候选不唯一、页面归属不明或无法验证时，停止视觉生成并问用户一个来源确认问题；不要按目录名、最近修改时间或 `latest` 后缀猜测。
4. 用户确认没有真实前端后，才降级到 `design-system`、`reference-html` 或 `screenshot`。截图推断要记录原图 hash，并明确哪些规范可观察、哪些生产组件和 token 未验证。
5. 没有任何可用视觉证据时，PRD 可继续写，但 HTML/截图状态停在 `source_resolution_required`，不得声称项目 UI 对齐。

来源选择和选择依据必须写入 `mockup-evidence.json`；详细字段和状态迁移见 `mockup-evidence-manifest.md`。

## Static HTML / Screenshot Criteria

以下情况必须补静态 HTML mockup 或 preview，并生成截图：

- 需求是一个现有页面上的新增状态、提示、弹窗、卡片、按钮区。
- 页面变化通过视觉位置更容易解释。
- 开发需要知道变更发生在哪个上下文。

PRD 中写清：

- 文件路径。
- 展示状态：默认态、拦截态、确认态、失败态、成功态。
- 是否基于真实组件结构复刻。
- 如果项目无法启动，明确标记“静态复刻，未运行真实应用”。
- 线上发布时截图应该插入的章节标题，避免后续发布器把图片集中放到“关联产物”。

## Prototype Match Gate

截图之前先判断原型能否代表本期目标。页面名称相似不等于结构一致；页面数量、一级导航、功能模块和关键状态至少要与 PRD 对得上。

| 原型状态 | 处理方式 | 能否作为目标态截图 |
| --- | --- | --- |
| 与 PRD 目标结构一致 | 实际渲染、截取关键状态、嵌入对应章节 | 可以 |
| 只代表当前线上状态 | 标注“现状参考”，用于解释改造前问题 | 不可以 |
| 页面、模块或状态与新 PRD 不一致 | 先更新静态 HTML，或转 UI 结构/正式 mockup Skill | 不可以 |
| 没有可用原型，但页面结构足够稳定 | 调用 `ui-mockup-desktop-workbench` 新建目标态 HTML/preview，再截图回填 | 生成并验证后可以 |
| 页面结构存在阻断性未决问题 | 先记录假设或停止视觉固化；说明受影响页面和待补动作 | 不可以 |

不得因为“已有一个 HTML 文件”就直接截图。只要页面、一级导航、功能模块或关键状态与目标 PRD 不一致，就必须先更新原型，或明确它只是现状/历史参考。具体历史失败应留在 regression fixture，不写成通用规则。

## Screenshot Execution Gate

只要 PRD 是页面型，页面证据就是本轮交付的一部分，不是后续建议：

1. 没有目标态 HTML/preview 时先生成；然后打开或渲染，确认页面不是空白、关键模块可见。
2. 每个发生实质变化的页面/模块至少截取一张默认态。
3. PRD 明确定义的关键失败态、空态、确认态或成功态，按关键状态覆盖需要补充截图。
4. 将图片嵌入对应功能/页面/状态章节，并在图片附近说明状态和检查重点。
5. 同一截图可以复用，但不能只集中放在文末“关联产物”或“本地草稿附录”。
6. HTML 或 UI 基线更新后，现有截图立即视为 stale。重新渲染后用 `capture_mockup_evidence.py` 记录 HTML hash、截图 hash 和截图来源 HTML hash。
7. 截图修改时间早于 HTML、截图来源 hash 与当前 HTML 不一致、或 PRD 没有引用 manifest 中的截图时，不得声明完成。

仅在以下情况允许跳过实际截图：

- 用户明确要求纯文本 PRD。
- 阻断性的页面信息架构或状态方案仍未关闭，截图会固化错误方案。
- 真实项目不可访问，且无法形成有证据的静态复刻。
- 截图/浏览器工具不可用，且没有可行替代路径。

跳过时必须在最终说明中写明原因、受影响页面和待补动作。“当前没有 HTML”“已经写了截图位置”“HTML 路径在附录里”都不属于有效理由。

## Publish-ready Placement

当用户提到 PRD 会上传到钉钉、飞书、Google Docs 或发给开发在线阅读时，按发布版写法处理 mock：

- 不要在文档信息表写 `关联 mock` 本地链接。
- 不要把 `.html`、`.png`、`dingtalk-assets`、`file://`、`localhost` 等路径作为正文阅读入口。
- 每个截图占位都要贴近它解释的功能模块，例如“选择文件后的输入框状态”“发送后的任务卡状态”“取消按钮状态”。
- 同一 mock 可以截图一次、复用多处说明，但正文中只保留用户和开发需要看的截图，不保留失败图或重复图。
- “关联产物”只适合本地草稿或最终交付说明；发布版 PRD 默认不生成这个章节。
- 如果仍需保留本地 mock 索引，放在 `本地草稿附录，不上传钉钉正文` 下。

## Diagram vs Mockup

| 情况 | 优先产物 |
| --- | --- |
| 解释页面区域、按钮、状态提示 | screenshot / HTML mockup |
| 解释主链路、状态流转、上下游依赖 | Draw.io flow |
| 解释模块关系、输入输出、支撑层 | Draw.io architecture |
| 需要正式多状态高保真 UI | `ui-mockup-desktop-workbench` |

## Required PRD Text

PRD 中至少写：

- 页面入口。
- 触发动作。
- 新增或变化区域。
- 用户可见反馈。
- 关键状态。
- 截图或 mock 应放入的对应章节。
- 可观察结果及其检查方式。

当页面证据门禁被触发时，还必须有：

- 实际生成的截图文件。
- 对应功能章节中的 Markdown 图片或等价的正文图片引用。
- 原型匹配结论：目标态、现状参考或结构不匹配。
- UI 来源种类、路径与 commit/hash；无法确定真实前端时的用户确认结果。
- `mockup-evidence.json` 路径及当前状态；只有通过新鲜度校验的截图可以作为目标态证据。

## Correction Mode

如果用户指出“不是这个页面 / 不是这种 HTML / 要基于真实项目展示”，立即：

1. 回到用户指定项目和模块，重新确认 repo 边界。
2. 找到真实页面入口组件、触发按钮和状态来源。
3. 把 PRD 页面结构改成“真实页面 + 新增状态/弹窗”。
4. 删除错误页面相关术语、截图和流程。
5. 保留真实业务规则并映射到真实动作上。

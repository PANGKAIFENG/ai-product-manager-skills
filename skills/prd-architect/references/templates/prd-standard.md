# PRD-standard Template

用于常规产品功能、多个页面状态或跨模块规则。目标是围绕目标态 UI 和功能逻辑完成产品、设计、研发、测试对齐，而不是机械展开固定章节。

## Output Skeleton

省略任何“按需”章节时，后续章节顺次重编号，不保留编号空档。

### 版本记录

放在 PRD 标题之后、文档信息之前。新建 PRD 使用 `V1.0`；修订已有 PRD 时保留旧记录并把最新版本置顶。

| 版本 | 日期 | 修改内容 |
| --- | --- | --- |
| V1.0 | YYYY-MM-DD | 首次创建 |

### 1. 背景与目标

- **背景**：最多用 200 字说明当前问题、主要影响和为什么现在处理；能更短说清就不要凑字数。不要写行业综述、过程复盘或长期愿景。
- **本期只解决**：一句话写清范围。
- **成功标准**：2-3 条可观察结果。
- **不做**：只列最容易造成范围误解的内容。

不单列“用户场景”。用户、触发和预期结果必须进入对应功能模块，避免和入口、页面结构、交互逻辑重复。

### 2. 核心流程（按需）

只有满足任一条件才启用本节：

- 跨越多个角色、系统或上下游模块，单看功能模块无法理解先后关系。
- 存在关键判断、回流、异步等待或失败恢复，文字表格难以表达。
- 主链路达到 6 个及以上步骤，并且步骤间依赖影响需求判断。
- 用户明确要求正式流程图或架构图。

启用时读取 `references/drawio-templates.md`，生成可编辑 Draw.io 源文件及可预览图。简单页面改动、单个弹窗或同页状态切换不画流程图，也不使用 Mermaid / ASCII 代替装饰。

### 3. 功能模块

正文主体。每个实质改动使用一个模块；不要再为入口、页面结构、核心对象和交互逻辑创建平行章节。

#### 3.x 模块名称

**模块目的**：一句话说明用户在这里完成什么，以及该模块为什么存在。

**目标态 UI**

页面型模块必须把目标态截图放在这里或对应状态小节。现状图只能标注“现状参考”，不能代替目标态。

将生成后的真实截图插入此处，例如：`![目标态：状态名称](path/to/screenshot.png)`。

**功能逻辑**

| 条件 / 状态 | 用户操作 | 系统行为 | UI 反馈 |
| --- | --- | --- | --- |
|  |  |  |  |

规则只写一次。截图已经表达清楚的布局不再用长段落复述；表格已经表达清楚的规则不再复制到背景或其他章节。每一行都要写清可观察的 UI 反馈或用户结果。

**状态语义（仅有歧义时）**

当状态名称相近但主体或作用域不同，必须拆开：

| 状态 | 主体 | 判定时点 | 影响范围 | 用途 |
| --- | --- | --- | --- | --- |
|  | 用户 / 成员 / 企业 / 任务 / 其他 |  |  |  |

**边界与异常（按需）**

只写会改变用户结果、系统反馈或恢复方式的边界。普通输入校验不扩写成长清单。

### 4. 跨模块规则（按需）

只有一条规则同时约束两个及以上模块时才启用。写一次并注明适用模块，不在每个模块复制。

### 5. 待确认事项（仅草稿 / 讨论中）

只列阻断决策或真实未决问题。发布版正文默认省略本节。

### 6. 本地草稿附录（按需）

只放本地协作材料。发布到钉钉或在线文档时默认省略，不放无法在线访问的本地路径。

## Compression Rules

- 背景不超过 200 字且不为凑字数扩写，正文不写调研过程。
- 不输出独立“用户场景”“入口与触发”“页面结构”“核心对象”“交互逻辑”章节。
- 每条信息只出现一次；优先放在最接近用户动作和 UI 状态的功能模块中。
- 页面变化优先用目标态截图表达，再用简短逻辑表解释。
- 不输出独立的“模块验收”“整体验收”或“验收标准”章节；可验证结果写进功能逻辑、UI 反馈和边界与异常。
- 没有新增信息的章节直接删除，不保留空标题或“无”。

## Handoff Boundary

只有用户明确要求开发 handoff、字段、接口协议、schema、metadata、adapter 或实现计划前置材料时，才加载 `references/handoff-appendix.md`。

# PRD-lite Template

用于单点改动、局部体验或轻量规则。目标是让读者在 5 分钟内看懂改什么、页面如何反馈、边界是什么。

不要单列“用户场景”“入口”“页面结构”“交互逻辑”来重复同一件事。把触发、行为和反馈写进对应功能模块。

## Output Skeleton

### 版本记录

放在 PRD 标题之后、文档信息之前。新建 PRD 使用 `V1.0`；修订已有 PRD 时保留旧记录并把最新版本置顶。

| 版本 | 日期 | 修改内容 |
| --- | --- | --- |
| V1.0 | YYYY-MM-DD | 首次创建 |

### 0. 文档信息

| 功能名 | 状态 | 模块 | 更新时间 |
| --- | --- | --- | --- |
|  | 草稿 / 讨论中 / 已确认 |  |  |

### 1. 背景与目标

- **背景**：最多用 200 字说明当前问题和为什么现在要改；能更短说清就不要凑字数，不写行业综述或长期愿景。
- **本期只解决**：一句话写清改动范围。
- **成功标准**：1-2 条可观察结果。
- **不做**：只有容易产生误解时才写。

### 2. 功能模块

每个实质改动使用一个模块，不为入口、页面结构或交互重复建章节。

#### 2.x 模块名称

**改动目的**：一句话说明该模块解决什么。

用户可见改动必须先放目标态 UI 截图；现状图只能标注为“现状参考”。

将生成后的真实截图插入此处，例如：`![目标态：状态名称](path/to/screenshot.png)`。

| 条件 / 状态 | 用户操作 | 系统行为 | UI 反馈 |
| --- | --- | --- | --- |
|  |  |  |  |

每一行都要写清可观察的 UI 反馈或用户结果。只补充表格无法表达的边界或异常，不复述截图中已经清楚的信息。

### 3. 待确认事项（仅草稿 / 讨论中）

只放阻断决策或真实未决问题。发布版正文默认省略本节。

## Diagram Rule

PRD-lite 默认不生成流程图。若出现多角色、多模块、上下游依赖、循环或多个关键判断，或用户明确要求正式图示，应升级为 `PRD-standard`；用户明确要求时直接生成 Draw.io，未明确要求时才应用复杂度门槛。不要用 Mermaid 或 ASCII 为简单改动补装饰性流程图。

## Optional Sections

- 多个模块共享同一条规则时，增加“跨模块规则”，只写一次。
- 用户明确要求开发字段时，加载 `references/handoff-appendix.md`，字段只进入附录。
- 页面型需求加载 `references/mockup-handoff.md`，完成 HTML、目标态截图和正文回填。

## Publish-ready Rules

- 不写本地 HTML、PNG、`file://`、`localhost` 或 `dingtalk-assets` 路径。
- 截图留在对应功能模块，不生成底部“关联产物”。
- 默认不输出“待确认事项”正文。

## Prohibited In Main Body

- TypeScript interface、JSON schema、endpoint、adapter 或 hidden metadata。
- 为了填模板而生成的用户场景、流程图或重复规则。
- 独立的“模块验收”“整体验收”或“验收标准”章节；可验证结果写进功能逻辑和 UI 反馈。

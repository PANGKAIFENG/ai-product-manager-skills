# Output Template

## 快速诊断（默认）

用中文回答，先用最小案例事实建立共同上下文。已有充分材料时不要反问；没有原话时标为摘要或缺失。事实层不是把诊断结论提前改写一遍。

````markdown
**案例事实**
- 用户要求（原话 / 摘要 / 未取得）：...
- 关键输入：图片、PDF、工程文件、用户选择等；内容是否取得。
- 预期与实际：应该交付什么；trace 实际记录了什么答复、服务状态和产物。
- 证据范围：完整会话 / 局部片段；客户端是否独立核实，缺少什么。

**核心判断**
<1-2 句：失败在哪里，原因已确认还是候选，后续动作如何放大损失。不能确认时直接说明。>

**执行流程图**
```mermaid
flowchart LR
  A["E1 用户要求"] --> B["E2 主链路调用"]
  B --> C["E3 失败点：请求未提交"]
  C --> D["E4 后续恢复动作"]
  D --> E["E5 实际输出"]
```
<只画实际存在的事件。诊断标签按证据强度添加：失败点 / 根因候选 / 已确认根因 / 放大因素。顺序不证明因果；推断关系用虚线。>

**证据链**
- `E1 已确认 / 推断 / 待验证`：事实；原始记录 ID 或来源定位。
- `E2 ...`

**其他问题与放大因素**
<如果存在，解释其独立影响。不要预设后续错误都只是症状。>

**代码位置**
<本轮实际读过的文件与行号；否则写候选路径和待验证。说明是否匹配历史部署。没有仓库则注明未核验。>

**优化与验证**
- 行为应如何改变、负责层、最小验证；不要承诺未经测量的节省收益。
````

## 可视化案例（按需）

用户要求 HTML 时读取 [replay-contract.md](replay-contract.md)，生成脱敏数据包后调用固定渲染器。不要把上面的 Markdown 整段塞进对话区，更不要把分析摘要伪装成助手消息。

阅读顺序固定为：真实问答 → 按需展开处理过程 → 单次关键参数/原始记录 → 独立问题分析。流程图放在分析区，不侵入默认对话。

## 共同规则

- 用户原话、附件元信息、工具实际参数与返回、分析摘要和推断分别标识。
- `E#` 对应证据；诊断引用证据，证据引用消息/调用/来源。图合并重复节点不等于删除记录。
- 不输出隐性思考；可以引用 trace 中公开文本，但没有客户端验证不能称为“当时已向用户展示”。
- 调用区间不当成纯推理耗时。主模型与工具分别计数；不把辅助标题调用算进主模型。
- 请求模型与实际执行模型分开；`auto` 不解释成确定型号，服务未接受不解释成已生成或已计费。
- 输出简短不等于省略事实层。用户只要一句话时，也用“用户要 X，实际 Y；可确认 Z，原因仍待核验”保留最小事实。
- 用户要求只读时说明未修改业务代码；生成报告时说明只创建了诊断产物，不笼统宣称“未修改任何文件”。

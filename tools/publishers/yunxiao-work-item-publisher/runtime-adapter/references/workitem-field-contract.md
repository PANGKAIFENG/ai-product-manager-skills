# 云效工作项字段契约

## 1. 类型判断

| 判断 | 使用 `缺陷` | 使用 `需求` |
| --- | --- | --- |
| 用户预期 | 已有能力本应可用 | 希望增加或扩展能力 |
| 当前表现 | 报错、回归、结果错误、必须绕路 | 能力不存在或范围不足 |
| 主要目标 | 恢复符合预期的行为 | 交付新的用户价值或治理能力 |
| 示例 | 安装 Skill 后必须重启才能使用 | 统一安装、更新、删除、回滚的生命周期治理 |

一项工作可能同时暴露缺陷和后续改进。当前异常先提缺陷；能够独立交付和验收的长期能力再提需求。不要为了容纳技术方案，把同一用户问题拆成多个平级工作项。

## 2. 颗粒度判断

默认一条工作项对应一个用户可观察结果。满足任一条件时才拆分：

- 两个结果可以独立上线且各自有完整验收标准；
- 两个结果面向不同用户或业务链路；
- 两个结果由不同责任边界承接，且任一结果不依赖另一项才成立；
- 一个是当前故障修复，另一个是非必要的长期增强。

以下内容通常是主工作项的子任务或实现建议，不单独提需求：目录同步、instance reload、配置生成、回归测试、日志埋点、接口回读。

## 3. 字段规则

| 字段 | 创建前要求 | 规则 |
| --- | --- | --- |
| 项目 | 必填 | 使用稳定项目 ID；同时展示项目名供人确认 |
| 类型 | 必填 | 只允许 `需求` 或 `缺陷`；映射到实时 MCP 返回的类型 ID |
| 标题 | 必填 | 描述一个用户问题或结果，不写实现步骤串联 |
| 描述 | 必填 | 使用证据描述模板，不把推断写成事实 |
| 优先级 | 必填 | 只允许 `紧急`、`高`、`中`、`低` |
| 迭代 | 可选 | 有明确目标时使用稳定 ID；不得只凭当前页面猜测 |
| 负责人 | 可选 | 使用成员 ID；重名时必须消歧 |
| 子模块 | 可选 | 使用模块 ID；找不到时保持空白并报告 |
| 客户名称 | 可选 | 只有用户明确提供或已有字段直接证明时填写 |

## 4. 优先级

- `紧急`：仅用于已验证的线上/安全事故、合规或合同期限、固定里程碑等硬约束。
- `高`：高影响可靠性问题、阶段核心结果、关键客户价值或多个事项的共同底座。
- `中`：有明确价值，但没有已验证的即时硬约束或影响范围较局部。
- `低`：可选体验优化、探索项或价值尚不清晰且不阻塞当前目标的事项。

没有硬约束证据时，不把“很重要”“尽快”自动映射成 `紧急`。

## 5. 标题规则

缺陷推荐：`【产品/模块】<触发动作>后<异常结果>`。

需求推荐：`【产品/模块】<目标能力或用户结果>`。

避免：

- 把多个结果用“以及、同时、并且”堆在一个标题中；
- 把具体代码方案写成产品标题；
- 使用“优化一下”“体验不好”这类不可验收表达；
- 将未经验证的根因直接写入标题。
